## The `clean` fixture's false start (v1) — a fixture-authoring bug, not a verifier flaw

The first version of the `clean` fixture used raw string literals (`'red'`,
`'blue'`) for `Widget.color`, while the fixture's own BC README defined
`Color` as "one of `red`, `blue`, `green`, represented as the `Color` enum,
**never as a raw string**." All 3 real verifier runs against `clean` v1
correctly `FAIL`ed under check 4 (ubiquitous language), citing exactly that
contradiction — a **correct catch of a real inconsistency I introduced by
accident** while authoring the fixture, not a false positive against
genuinely clean code.

| Fixture | Expected (intended) | Run 1 | Run 2 | Run 3 |
|---|---|---|---|---|
| `clean` (v1, raw strings — fixture bug) | PASS | FAIL (check 4) | FAIL (check 4) | FAIL (check 4) |

Fixed by introducing a real `Color` enum (`Object.freeze({RED,BLUE,GREEN})`)
and having both the implementation and tests reference `Color.RED` /
`Color.BLUE` instead of literal strings (see `fixtures/clean/src/widget.js`,
`fixtures/clean/test/widget.test.js`). Re-run (v2, above) came back
`PASS` 3/3.

**Lesson**: this eval's own construction process demonstrated the verifier
enforcing README wording completely literally, including
representation-level details ("never as a raw string"). That's arguably
correct behavior per "On being strict" in `agents/verifier.md`, but it means
fixture (and, by extension, real BC README) authors must keep such
constraints precise — a loosely worded README clause can trip the gate on
code that a human would call "clean." No verifier-prompt defect is implied;
this is filed as a lesson, not a follow-up capture against the verifier
itself.
